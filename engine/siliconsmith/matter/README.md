# Matter engine (MatterCompiler-lite): 2D heat solver

Scope: a thin plate of thickness `t` with a rectangular heat source, material mask `m(x, y)`, convection to ambient from both faces.
The physics is ours (this solver), not the model's. Agent-written geometry generators will run on top of it later.

## Model

Steady state, per unit plate area:

    -div(k t grad T) + 2 h (T - T_inf) = q

Finite volume on a regular square grid (cell size `dx`), unknowns at cell centres, SciPy sparse direct solve.
`k` is zero outside the material, so face conductance uses the harmonic mean and a material/void face is adiabatic.
The outer boundary is adiabatic except optional fixed-temperature edges (`left|right|bottom|top`), imposed at the face.
The source is a cell-index rectangle with total power `Q` spread evenly over its cells; every source cell must be material.

Units: m, W, K (differences), `k` in W/(m K), `h` in W/(m^2 K). Arrays are `[j, i]` (row = y, column = x).

## API

`solve(mask, dx, k, t, h, T_inf, source, fixed_edges, T_fixed) -> Result` with `T` (NaN off-material), `peak`, `Q_in`,
`Q_conv`, `Q_fixed` (negative = heat entering through a fixed edge), `balance_rel`, `solve_residual_rel`.
`connected_to_source(mask, source)` checks that all material is 4-connected to the source.

## Validation

`thresholds.py` was committed before any result existed and is never edited after seeing results.
"Validated" means only: agrees with an analytic case within those thresholds.
Run `python -m siliconsmith.matter.validate --write` to regenerate `VALIDATION.md` (measured numbers); tests are in `engine/tests/test_matter_solver.py`.

## Honest limits

* 2D plate model: no through-thickness gradients, no fins in the third dimension.
* Steady state only; no transients.
* `h` and `k` are stated inputs, not measured; convection is a constant coefficient, no airflow CFD, no radiation.
* Not validated on a printed part. Only the analytic straight fin, the analytic radial disc (equivalent radii of the staircase disc) and a grid-convergence study have been checked.
* Not yet done: the 3D viewer (web app), deployment and load testing of the hosted functions.
* Grid convergence order of the peak temperature is not clean (observed 1.1 then 4.1 between successive levels); only the 2x-difference threshold is claimed.

## Workbench pieces (all in this package)

| File | Role |
|---|---|
| `solver.py` | primary finite-volume solver (validated, see `VALIDATION.md`) |
| `fem.py` | second solver: bilinear FEM, consistent mass, ILU-preconditioned CG; shares no code with `solver.py` |
| `problem.py` | the heat-spreader template (`Spreader`), M2 validity, M3 printability, swept rectangular-fin baseline |

| `serverless.py`, `api.py`, `limits.py`, `HOSTING.md` | hosted `simulate` / `run_agent`, HTTP handler + FastAPI router, validation, rate-limit hook |
| `ladder.py` | rungs M1..M5 with the exact plan labels |
| `export.py` | STL (extruded mask, closed-surface checked), results JSON, sha256 |
| `agent.py` | Nemotron loop: Ultra proposes generator ideas from measured results, Super writes the code; we run everything else |
| `evals.py` | plan section 10 evals as code; re-derives each winner from saved files |
| `reference_generators.py` | hand-written examples used in tests and shown to the model (not model output) |

Run it: `python -m siliconsmith.matter.agent --rounds 3 --ideas 3 --max-usd 1.5` (needs `NEBIUS_API_KEY`; events go to `runs/logs/<run_id>.ndjson`, artifacts to `runs/matter/<run_id>/`).

## Rungs and what they mean

* M1 the validation suite passes (analytic fin 1%, 2x refinement 2%, balance). Run once per run, before any agent code.
* M2 mask is bool, right size, within the material budget (chip footprint counted), all connected to the chip.
* M3 minimum feature 2 cells (morphological opening), one piece, no enclosed voids.
* M4 independent FEM solver and 2x refinement agree on the peak rise within 3% / 2%.
* M5 beats the best plain rectangular-fin plate that uses no more material than the candidate (a swept baseline, not one hand-picked design). It says nothing about the full-budget baseline; the report states that separately.

## Isolation, stated honestly

See `HOSTING.md` (security model). Short version: generators run in a Token Factory Sandbox (`runners.SandboxRunner`, network namespace, fail-closed) or in a scrubbed local subprocess for development; the process holding secrets never runs them. The in-worker screen is best effort; the boundary is where the code runs.

## Evidence

`EVALS.md` (generated by `evals.py --runner sandbox`) and `evidence/m_v3_{1,2,3}/` hold three real Nemotron runs: 6 rounds x 3 ideas, generator code executed in real Token Factory Sandboxes, about $0.09 to $0.11 and 3.5 to 4 minutes each. Each winner is re-derived from its saved code in a Sandbox and reproduces exactly (numpy versions differ by a cell at some edges between host and sandbox, so re-derive in the same kind of place).

| config | runs beating equal-material baseline | runs beating full-budget baseline | winner peaks (C) |
|---|---|---|---|
| v2: 4 rounds, no field feedback | 3/3 (+0.48, +0.11, +0.25 K) | 1/3 | 76.24, 100.13, 72.57 |
| v3: 6 rounds, hot-spot / idle-material feedback | 3/3 (+0.26, +0.26, +0.22 K) | 3/3 | 72.56, 72.56, 72.60 |

Reading it honestly:
* v3 is more **consistent** (3/3 reach about 72.6 C and beat both baselines) but not materially **better**: it converges to the same ~0.25 K margin.
* There is a hard physical floor. With 1440 cells of material and convection only, no geometry can be cooler than 71.30 C (every cell isothermal; `problem.isothermal_bound`). The best plain-fin baseline is already 72.82 C, so the whole headroom is 1.52 K and the agent closes about 17% of it. The problem as posed (2 W, 40% material, convection only) leaves little room for a "much better" shape; larger gains need a harder setup (for example a smaller material budget or a hotter chip), not a better model.
* Margins are model estimates under stated k and h; they do not claim the printed part would measure 0.25 K cooler.
* The v2 runs and an earlier v1 set are superseded and not kept as evidence.
The run's "winner" is the lowest-peak node that passed M1-M5; `result.verdict` reports both baselines and the lower bound.
